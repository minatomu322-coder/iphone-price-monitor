# TCG 利益商品 日次抽出システム 設計案（BS提出用）

対象タイトル：**ポケモンカード / ワンピースカードゲーム / ドラゴンボールスーパーカードゲーム フュージョンワールド**
目的：**BS提出用の「利益が取れる商品」を 1日1回・合計15件、短期／中期／長期の3パターンで自動出力する。**

---

## 0. 決定事項（ヒアリング済み・この前提で設計を確定）

| 項目 | 決定内容 | 設計への影響 |
|---|---|---|
| 出口（販売先） | **メルカリ／買取店／ヤフオク等フリマ／業者間卸 の4チャネル併用** | 出口価格を1つに固定せず、**チャネル別に手取り額を計算して最良チャネルを選ぶ**設計にする（§4.2） |
| 1商品の仕入上限 | **上限なし** | 金額での足切りをしない。代わりに**高額品ほど流動性・真贋・資金拘束のリスク重みを上げる**（§6.4） |
| 提出形式 | **スプレッドシート／CSV** | CSVを第一級の出力とし、列定義を確定（§7）。Discordは要約通知のみ |
| 仕入先 | **ネット通販中心＋フリマの安値拾い** | 通販は全自動取得。フリマは規約上、自動取得せず**「探索キーワード＋指値」を提示する半自動方式**（§4.3） |

## 1. 全体像

```
[1] 価格収集      毎日 1〜2回、各サイトから「売値（販売相場）」と「買値（買取相場）」を取得
        ↓
[2] 蓄積          SQLite に日次スナップショットで保存（履歴＝トレンド判定の資産）
        ↓
[3] 指標計算      1商品ごとに 現在値/騰落率/ボラ/スプレッド/在庫/流動性 を算出
        ↓
[4] 3戦略スコア   短期・中期・長期でそれぞれ別のスコア式にかける
        ↓
[5] 選定          各戦略 上位5件（計15件）／直近N日に出した商品は除外
        ↓
[6] 出力          BS提出フォーマット（Markdown＋CSV）＋ Discord通知
        ↓
[7] 実績反映      提出後の採用可否・実売結果を記録し、スコア係数を補正
```

実行基盤は既存と同じ **GitHub Actions の cron（1日1回 JST 朝）**、保存は **SQLite をリポジトリにコミット**、通知は **Discord Webhook**。
新規インフラ・課金なしで回せる構成を維持する。

## 2. 既存コードとの関係（流用と差分）

| 既存 | カード版での扱い |
|---|---|
| `scraper.py`（requests + BS4、リトライ/UA/IPv4固定） | ほぼそのまま基盤として流用。サイトごとのパーサだけ `sources/` に分割 |
| `database.py`（日次スナップショット＋diff） | テーブルを拡張。「原価固定」から「**買値・売値の両方が動く**」二面モデルへ |
| `decision.py`（しきい値判定） | `strategy.py` に置換。3戦略のスコアリングへ拡張 |
| `notifier.py`（Discord） | 流用。フォーマットのみ差し替え |
| `main.py` / Actions cron | 流用。30分毎 → **1日1回**（＋任意で夜1回の2点観測） |
| `app.py`（ローカルダッシュボード） | 流用可。候補一覧の閲覧UIとして再利用 |

**最大の設計差分**：iPhoneは `cost_price` が固定値（既に買った物の含み損益管理）。
カードは **「いくらで買えるか」も毎日動く** ため、`仕入候補価格` と `出口価格` の2系統を別々に収集し、その差＝利益を毎日計算する。

## 3. データモデル（案）

```sql
-- 商品マスタ（監視対象カード／BOX）
CREATE TABLE products (
  product_id   TEXT PRIMARY KEY,   -- 例: pkm_sv8a_202_sar
  title        TEXT NOT NULL,      -- pokemon / onepiece / fusionworld
  name         TEXT NOT NULL,      -- カード名 or 商品名
  set_code     TEXT,               -- 収録弾（例: SV8a / OP-09 / FB-05）
  card_no      TEXT,               -- 型番
  rarity       TEXT,               -- SAR/SR/UR/AR/パラレル/BOX 等
  form         TEXT,               -- single / box / promo / graded
  release_date TEXT,
  jan          TEXT,
  active       INTEGER DEFAULT 1
);

-- 日次価格スナップショット（買値・売値の両方をここに入れる）
CREATE TABLE product_prices (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  observed_at  TEXT NOT NULL,
  product_id   TEXT NOT NULL,
  source       TEXT NOT NULL,      -- 駿河屋 / 楽天 / Yahoo / 各買取店 …
  side         TEXT NOT NULL,      -- 'buy'（自分が仕入れる価格） / 'sell'（自分が売れる価格）
  condition    TEXT,               -- 新品未開封 / A / B / 傷あり / PSA10 …
  price        INTEGER NOT NULL,
  stock        INTEGER,            -- 在庫数（取れる場合）
  url          TEXT NOT NULL,
  raw_text     TEXT
);

-- 日次の集計指標（[3]の出力をキャッシュ）
CREATE TABLE product_metrics (
  as_of        TEXT NOT NULL,
  product_id   TEXT NOT NULL,
  buy_min      INTEGER,  -- 最安仕入価格
  sell_ref     INTEGER,  -- 出口価格の基準値（中央値）
  spread       INTEGER,  -- sell_ref - buy_min
  net_profit   INTEGER,  -- 手数料・送料控除後の想定利益
  margin       REAL,     -- net_profit / buy_min
  chg_7d       REAL, chg_30d REAL, chg_90d REAL,
  volatility   REAL,     -- 30日標準偏差 / 平均
  liquidity    REAL,     -- 直近の売れ行き・出品数から算出
  stock_total  INTEGER,
  PRIMARY KEY (as_of, product_id)
);

-- 提出履歴（重複提出の防止＋実績フィードバック）
CREATE TABLE submissions (
  submitted_on TEXT, product_id TEXT, strategy TEXT,
  buy_price INTEGER, expect_sell INTEGER, expect_profit INTEGER,
  result TEXT,          -- adopted / rejected / bought / sold
  actual_profit INTEGER,
  PRIMARY KEY (submitted_on, product_id)
);
```

## 4. データソースと出口チャネル

### 4.1 仕入側（buy）— どこでいくらで買えるか

**2026-09-08 に GitHub Actions から実測した到達性**（`tcg/probe.py`）：

| サイト | 結果 | 判断 |
|---|---|---|
| 駿河屋 | 403（Cloudflare チャレンジ） | **不採用**。回避策は取らない |
| ドラゴンスター買取／遊々亭／cardrush.media | 403 | 不採用 |
| C-labo | 200 だが「2026-08-30 ネット買取受付停止」 | 不採用（価格が凍結している可能性） |
| カードラッシュ通販（3タイトル別ドメイン） | 200・robots 許可 | **採用（buy側）** |
| トレトク 買取価格表 | 200・robots 許可 | **採用（sell側・ポケカ／ワンピ）** |
| PRICE BASE 買取表 | 200・robots 許可（Crawl-delay 5） | **採用（sell側・3タイトル）** |
| 楽天／Yahoo!ショッピング API | 401（キー無し）＝到達OK | 採用（要キー） |

**A. 公式API（安定・合法）**
- 楽天市場 商品検索API … 2026-02 の基盤更新で `openapi.rakuten.co.jp` へ移行し、`applicationId` に加え `accessKey` が必須
- Yahoo!ショッピング API（Client ID で無料）

**B. 公開ページの取得（1日1回・間隔3〜5秒・robots.txt 尊重）**
- カードラッシュ通販 … 検索結果から型番一致の販売価格・在庫（buy側）
- トレトク／PRICE BASE の買取表 … タイトルごとに1ページ取得して全商品を照合（sell側 kaitori）

キー無しでもカードラッシュ＋買取表で両側が揃うため、短期パターンは初日から動く。

### 4.2 出口側（sell）— 4チャネルを並べて「最良の手取り」を選ぶ

出口を1つに固定せず、チャネルごとに手取り額を計算し、**最も手取りが高いチャネルを推奨出口として提示する**。

| チャネル | 手数料 | 想定売価の取得方法 | 回転 |
|---|---|---|---|
| メルカリ | 10% ＋ 送料 | 公式APIなし → **手動更新の相場シート**（§4.3）で補完 | 速い |
| ヤフオク／その他フリマ | 約10% ＋ 送料 | 落札相場（取得可能な範囲で）／メルカリ相場を代理値に | 速い |
| 買取店（駿河屋・専門店） | 0%（送料のみ） | **買取表を自動取得＝最も確実なデータ** | 最速・確実 |
| 業者間卸・BS経由 | 掛け率（設定値） | 買取上限 × 掛け率で近似 | 速い・大口可 |

出力には `推奨出口` と `各チャネルの手取り比較` を併記する。
「メルカリなら+3,200円だが2週間かかる／買取店なら+1,800円で即日」といった判断材料をそのまま提出物に載せる。

### 4.3 フリマの扱い（安値拾い・規約リスク回避）

メルカリ等は公式APIが無く、自動巡回は規約上のリスクがあるため**スクレイピングしない**。代わりに：

- **相場シート（`data/flea_market_prices.csv`）を人が週1で更新** → 出口価格の基準に使う
- 仕入側は、システムが **「探索キーワード＋指値（この金額以下なら買い）」を毎日提示** し、
  実際の検索・購入は人が行う**半自動方式**にする

例：`検索: "ピカチュウex SAR 202/187" ／ 指値: 12,800円以下なら利益率20%確保`

これにより「フリマの安値拾い」を、規約リスクを負わずに日次のアクションリストとして回せる。

## 5. 監視対象の作り方（「1日15個」の母集団）

15件出すには、母集団は **300〜800商品** 程度必要（スコア上位だけを出すため）。

| タイトル | 監視対象の作り方 | 目安件数 |
|---|---|---|
| ポケモンカード | 直近2年の主要弾の高額枠（SAR/SR/AR）＋人気キャラ＋未開封BOX＋旧裏/絶版の定番 | 300 |
| ワンピースカード | 各弾のリーダーパラレル/SEC/マンガレア＋BOX＋プロモ | 200 |
| フュージョンワールド | 各弾SCR/SR＋BOX＋プロモ | 150 |

構築手順：各サイトの「高額ランキング／売れ筋」ページから自動で候補を吸い上げ → `products` に自動登録（`auto_discovery`）。
手動メンテを最小化するため、**新弾発売日をカレンダー化**して発売前後で自動的に監視対象へ追加する。

## 6. 3パターンの定義とスコア式（案）

前提の利益計算（すべて共通）：

```
想定売価 sell_ref（出口の中央値、状態別）
- 販売手数料（メルカリ10% / ヤフオク10% / 買取店0%）
- 送料（ネコポス210〜／宅急便コンパクト等、form別に定数）
- 梱包資材（30円）
- 仕入価格 buy_min（送料込み）
= 純利益 net_profit    ／    利益率 margin = net_profit / buy_min
```

### ① 短期（回転 3〜14日）— 「今日のサヤ」で取る
今日のデータだけで判定できるため、**蓄積ゼロの初日から出せる**。
- 条件：`margin ≥ 15%` かつ `net_profit ≥ 1,500円` かつ 在庫あり かつ 流動性 上位
- 主な根拠：販売最安 vs 買取上限のスプレッド／急騰（`chg_7d ≥ +8%`）／在庫薄／大会・イベント直前
- スコア：`0.40×margin + 0.30×liquidity + 0.20×chg_7d + 0.10×(在庫の薄さ)`
- リスク：値動きが速い。**仕入当日〜翌日に売る**前提で提示する。

### ② 中期（1〜3ヶ月）— 「発売直後の底」を拾う
- 条件：`margin ≥ 25%`、発売後30〜90日、`chg_30d` が下落から**反転**、再録リスク低
- 主な根拠：新弾はパック開封が集中する発売直後に相場が底を打ち、供給が止まると戻る動き
- スコア：`0.35×margin + 0.25×(底打ち反転シグナル) + 0.20×liquidity + 0.20×(下落からの戻り余地)`
- 必要な蓄積：**30〜60日**の履歴

### ③ 長期（6ヶ月〜1年+）— 「絶版・供給停止」を寝かせる
- 条件：`margin ≥ 40%`、供給停止（再販終了/絶版）、`chg_90d ≥ 0`、ボラ低め
- 主な根拠：絶版タイトル、プロモ、初版、鑑定（PSA/BGS）需要、長期右肩上がり
- スコア：`0.30×margin + 0.30×(長期トレンドの傾き) + 0.20×希少性 + 0.20×(低ボラ)`
- 必要な蓄積：**90日以上**（初期は外部の年次相場データ or 手動シードで補う）

### ④ 高額品のリスク補正（仕入上限なしの前提での安全弁）

金額での足切りをしない代わりに、**仕入額が上がるほどスコアを割り引く**補正を全戦略に共通で掛ける。

```
risk_factor = 流動性係数 × 真贋係数 × 資金拘束係数
  流動性係数 : 直近の売れ行きが薄い高額品ほど小さくなる（売れ残りリスク）
  真贋係数   : 高額シングルは偽物・すり替えリスクがあるため、
               鑑定済(PSA/BGS)＝1.0 / 未鑑定の高額生カード＝0.7 など
  資金拘束係数: 仕入額が大きいほど小さくなる（1商品に資金が偏るのを避ける）
final_score = base_score × risk_factor
```

10万円のカードで利益率20%と、1万円のカードで利益率20%は同じ点数にはしない。
また **1日の提出15件のうち、高額品（10万円超）は最大3件まで**とし、資金が偏らないようにする。

**選定ルール**：各戦略 上位5件＝15件／日。
- 同一商品は **直近14日** 再提出しない（`submissions` で管理）
- 1タイトルに偏らないよう、戦略ごとに 3タイトルから最低1件ずつ確保
- データ不足で条件を満たす商品が5件に満たない場合は、**水増しせず「該当なし」と明示**する

Discordには「15件の要約＋CSVへのリンク」だけを1通投げる。
Googleスプレッドシートへ直接書き込みたい場合は、サービスアカウント＋gspreadで追記する拡張を後付けできる（Phase 2以降）。

## 8. 実装フェーズ（現実的な順序）

| Phase | 内容 | 期間 | この時点で出せるもの |
|---|---|---|---|
| 0 | 商品マスタ＋価格収集（楽天/Yahoo/駿河屋）を毎日蓄積、DB・Actions整備 | 1〜2日 | （まだ提出なし・データ蓄積開始） |
| 1 | 利益計算＋**短期パターン**を稼働、Discord/CSV出力 | +2日 | **短期5件/日** |
| 2 | 監視対象を数百件に拡大、買取表ソース追加、流動性指標 | +3日 | 短期の精度向上 |
| 3 | 履歴30日到達 → **中期パターン**追加 | 発売30日後 | 短期5＋中期5 |
| 4 | 履歴90日到達 → **長期パターン**追加＝15件/日 完成 | 90日後 | **15件/日** |
| 5 | 提出実績のフィードバックでスコア係数を自動補正 | 随時 | 精度改善 |

**正直な前提**：中期・長期は履歴が資産なので、初日からフル15件を精度よく出すことはできない。
急ぐ場合は、Phase 1〜2 の短期を厚めに（例：短期10＋中期3＋長期2）で開始し、蓄積に応じて 5/5/5 に寄せていくのが現実的。

## 10. 残っている論点（実装しながら詰める）

1. **1日の総仕入予算**：1商品の上限は無しと決まったが、**1日／1ヶ月の総枠**があれば、15件の合計仕入額が枠に収まるよう選定に制約を入れられる
2. **メルカリ相場シートの初期データ**：週1更新の運用は決まったので、初回だけ主要商品の相場を入れる必要がある（100件程度からで可）
3. **業者間卸の掛け率**：`rate_of_kaitori`（買取上限に対する掛け率）の実勢値
4. **監視対象の初期リスト**：自動収集で作るが、「これは必ず入れてほしい」定番があれば先に登録する
5. **Googleスプレッドシート直書き**：CSVコミットで足りるか、シートへ自動追記まで要るか（後付け可能）
